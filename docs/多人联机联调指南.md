# 多人联机联调指南

本文用于两台电脑验证当前“可选单人/多人、可选轮流/同时”的多人原型。当前网络层是 HTTP + 轮询，服务端权威执行行动。

## 1. 联调目标

本轮重点验证：

1. 两台电脑可连接同一个 HTTP 多人服务。
2. HTTP 多人房间可创建、加入、开始、重连、离开。
3. `sequential` 轮流回合和 `simultaneous` 同时回合都可玩至少一整轮。
4. 服务端权威生效：只能操作自己绑定的玩家。
5. 断线/退出提示生效：普通玩家离线可重连，房主退出会关闭房间。
6. UI 不依赖控制台也能看懂当前房间、客户端、玩家、等待、离线、关闭状态。

## 2. 设备分工

假设：

- 电脑 A：作为服务端 + 房主客户端。
- 电脑 B：作为加入方客户端。
- 两台电脑在同一局域网内。
- 两台电脑代码版本一致，建议都切到同一个 commit。

后续命令都在项目根目录执行：

```bash
cd /Users/ruiling/Desktop/未命名文件夹/gei-world
```

如果另一台电脑路径不同，进入它自己的 `gei-world` 项目根目录即可。

## 3. 联调前检查

### 3.1 两台电脑确认代码和依赖

两台电脑都执行：

```bash
git status --short
./.conda/bin/python -m pytest
```

期望：

- `git status --short` 没有非预期改动。
- 测试通过，当前基线应为 `102 passed`。

### 3.2 电脑 A 获取局域网 IP

macOS 可执行：

```bash
ipconfig getifaddr en0
```

如果没有输出，可试：

```bash
ipconfig getifaddr en1
```

记下输出 IP，例如：

```text
192.168.1.23
```

下文用 `<A_IP>` 表示电脑 A 的局域网 IP。

### 3.3 电脑 A 启动 HTTP 多人服务

电脑 A 执行：

```bash
./.conda/bin/python scripts/multiplayer_http_server.py --host 0.0.0.0 --port 8000
```

期望控制台显示：

```text
多人 HTTP 服务已启动: http://0.0.0.0:8000
```

保持这个终端不要关闭。

### 3.4 电脑 B 验证能访问服务

电脑 B 执行：

```bash
./.conda/bin/python scripts/remote_multiplayer_demo.py --url http://<A_IP>:8000 --turn-mode simultaneous
```

期望：

```text
✓ HTTP 远端多人流程完成
```

如果失败，优先检查：

- 两台电脑是否同一 Wi-Fi / 局域网。
- `<A_IP>` 是否正确。
- 电脑 A 防火墙是否阻止 Python 接入。
- 端口 `8000` 是否被占用或被拦截。

## 4. UI 联调总入口

两台电脑都启动 UI：

```bash
./.conda/bin/python scripts/ui_game.py
```

开始界面按键：

- `SPACE`：单人轮流。
- `T`：单人同时。
- `M`：本机多人原型。
- `H`：HTTP 多人表单。
- `L`：加载。
- `ESC`：退出确认。

HTTP 表单字段：

- 服务地址：`http://<A_IP>:8000`
- 房间 ID：例如 `room_1`
- 客户端 ID：例如 `client_1`
- 玩家名：例如 `玩家1` / `玩家2`
- 回合模式：`sequential` 或 `simultaneous`

创建/加入/重连成功后，UI 会在消息栏、开始界面或多人面板显示最近的房间 ID 和客户端 ID；再次打开 `H` 表单时也会自动预填最近记录。

游戏中如需退出当前局，点击顶部“主菜单”按钮；多人房间会先执行离开，房主返回主菜单会关闭房间。

## 5. 用例 A：单人模式冒烟

电脑 A 或 B 任意一台验证即可。

### A1. 单人轮流

步骤：

1. 开始界面按 `SPACE`。
2. 选中移民，按 `B` 或点击建城。
3. 点击结束回合。
4. 等 AI 行动后回到玩家视角。

期望：

- 可建城。
- 可结束回合。
- AI 行动后没有卡死。
- 仍可继续操作。

### A2. 单人同时

步骤：

1. 回到开始界面后按 `T`。
2. 玩家行动后结束回合。
3. 观察 AI 是否自动完成当前整轮。

期望：

- UI 显示同时回合。
- 玩家结束后不能继续行动。
- AI 自动处理后进入下一轮或给出等待/结果提示。

## 6. 用例 B：HTTP 同时回合双机联调

这是最重要用例。

### B1. 创建等待房

电脑 A：

1. 开始界面按 `H`。
2. 服务地址填：`http://<A_IP>:8000`
3. 玩家名填：`玩家1`
4. 回合模式填：`simultaneous`
5. 点击“仅创建等待房”。
6. 记录消息栏里的房间 ID 和客户端 ID，例如：
   - 房间 ID：`room_1`
   - 房主客户端 ID：`client_1`

期望：

- UI 提示 `HTTP 房间已创建：room_x，客户端：client_x`。
- 此时电脑 A 仍在开始界面，等待另一客户端加入。

### B2. 加入房间并开始

电脑 B：

1. 开始界面按 `H`。
2. 服务地址填：`http://<A_IP>:8000`
3. 房间 ID 填电脑 A 记录的 `room_x`。
4. 玩家名填：`玩家2`
5. 回合模式填：`simultaneous`
6. 点击“加入房间”。
7. 进入游戏后，在右侧多人面板记录自己的客户端 ID，例如 `client_2`。

期望：

- 电脑 B 进入游戏。
- 当前玩家是 `玩家2`。
- 多人面板显示房间号、客户端 ID、席位状态。

### B3. 房主重连进入同一局

电脑 A：

1. 开始界面按 `H`。
2. 服务地址填：`http://<A_IP>:8000`
3. 房间 ID 填 `room_x`。
4. 客户端 ID 填房主客户端 ID，例如 `client_1`。
5. 点击“重连房间”。

期望：

- 电脑 A 进入游戏。
- 当前玩家是 `玩家1`。
- 两台电脑看到同一个房间号。

### B4. 同时回合行动验证

电脑 A 和 B：

1. 双方各自选中自己的移民。
2. 双方都尝试建城或移动。
3. 电脑 A 点击结束回合。
4. 电脑 B 观察面板，再点击结束回合。

期望：

- 两名玩家在同一回合内都可行动。
- 电脑 A 结束后，电脑 A 显示本回合已结束/等待；电脑 B 仍可行动。
- 电脑 B 结束后，整轮推进到下一回合。
- 最近事件中能看到结束回合/推进回合相关提示。

## 7. 用例 C：HTTP 轮流回合双机联调

重复用例 B，但回合模式改为：

```text
sequential
```

重点验证：

1. 电脑 A 创建等待房时填 `sequential`。
2. 电脑 B 加入时也填 `sequential`。
3. 电脑 A 重连后先行动。
4. 电脑 B 在玩家1未结束前应不可行动或操作失败提示“还没轮到该玩家行动”。
5. 电脑 A 结束回合后，电脑 B 可行动。
6. 电脑 B 结束后，回合回到电脑 A 或推进整轮。

期望：

- 严格轮流。
- 服务端不允许越权行动。
- UI 能清楚显示当前可行动状态。

## 8. 用例 D：离开、重连、房间关闭

建议在同时回合房间中验证。

### D1. 普通玩家离线与重连

电脑 B：

1. 游戏中按 `Q`。
2. 确认离开房间。
3. 回到开始界面。

电脑 A 观察：

- 消息栏应提示 `玩家2 已离线`。
- 右侧多人面板应显示玩家2离线。

电脑 B 重连：

1. 开始界面按 `H`。
2. 服务地址填 `http://<A_IP>:8000`。
3. 房间 ID 填原房间 ID。
4. 客户端 ID 填电脑 B 之前记录的客户端 ID，例如 `client_2`。
5. 点击“重连房间”。

期望：

- 电脑 B 回到原房间和原玩家视角。
- 电脑 A 看到 `玩家2 已重新连接`。

### D2. 房主退出关闭房间

电脑 A：

1. 游戏中按 `Q`。
2. 确认离开房间。

电脑 B 观察：

- 消息栏应提示 `房主已退出，房间关闭`。
- 多人面板显示房间已关闭。
- 结束回合/建城/移动等操作不可继续或会失败提示。

期望：

- 房主退出后房间关闭。
- 普通玩家不能再重连或继续行动。
- UI 不崩溃。

## 9. 用例 E：异常与错误提示

### E1. 服务地址错误

任意电脑：

1. 开始界面按 `H`。
2. 服务地址填：`http://127.0.0.1:9`
3. 点击“创建调试房”或“仅创建等待房”。

期望：

- UI 提示连接失败。
- 不崩溃，不进入半局状态。

### E2. 房间 ID 错误

电脑 B：

1. 服务地址填正确地址。
2. 房间 ID 填不存在的 ID，例如 `room_missing`。
3. 点击“加入房间”。

期望：

- UI 提示房间不存在或加入失败。
- 仍停留在开始界面或可重新打开表单。

### E3. 客户端 ID 错误

任意电脑：

1. 服务地址和房间 ID 填正确。
2. 客户端 ID 填不存在的 ID。
3. 点击“重连房间”。

期望：

- UI 提示客户端不在房间中或连接失败。
- 不崩溃。

## 11. 通过标准

本轮联调可判定通过，需要满足：

- 自动化测试仍通过：`102 passed`。
- 两台电脑可通过 `http://<A_IP>:8000` 连接同一服务。
- HTTP 同时回合可完成至少一整轮。
- HTTP 轮流回合可完成至少一整轮。
- 普通玩家离开后，另一方看到离线提示；该玩家可用客户端 ID 重连。
- 房主退出后，另一方看到房间关闭提示，且不能继续行动。
- 错误服务地址、错误房间 ID、错误客户端 ID 不会导致 UI 崩溃。

## 13. 非同局域网联机方案

可以做到不在同一个局域网也能联机。当前代码已经是 HTTP 客户端连接服务端模型，关键是让两台电脑都能访问同一个服务地址。

推荐方案按优先级：

1. 公网服务器/云主机部署：把 `scripts/multiplayer_http_server.py` 跑在有公网 IP 或域名的机器上，客户端服务地址填 `http://公网IP:端口` 或域名。这是最适合当前回合制 HTTP 原型的方案。
2. 临时隧道：用 Cloudflare Tunnel、ngrok、Tailscale Funnel 等把电脑 A 的本地 `8000` 端口暴露成公网 HTTPS 地址，适合短期联调，不适合长期正式服。
3. VPN/虚拟局域网：两台电脑加入同一个 Tailscale、ZeroTier 或自建 VPN 网络，然后继续按局域网方式联调。
4. P2P/NAT 穿透：需要引入房间协调服务、STUN/TURN/中继和更复杂连接管理，工作量明显更大；当前阶段不建议优先做。

当前建议：下一轮若要验证公网联机，先做“公网 HTTP 服务部署/隧道联调”文档和脚本参数打磨，不急着做 P2P。

注意：当前 HTTP 服务还没有账号、房间密码、TLS、限流和鉴权；如果暴露到公网，只建议短时联调用，正式公网服需要先补安全能力。

## 14. 常见问题

### 电脑 B 连不上电脑 A

检查：

1. 电脑 A 是否用 `--host 0.0.0.0` 启动服务。
2. 电脑 B 使用的是否是电脑 A 的局域网 IP，而不是 `127.0.0.1`。
3. 两台电脑是否在同一局域网。
4. macOS 防火墙是否拦截 Python。
5. 端口 `8000` 是否被占用，可换成 `8001`，两边地址同步改成 `http://<A_IP>:8001`。

### 加入成功但房主不知道怎么进入

当前流程是：房主先“仅创建等待房”，加入方加入后会启动房间；房主需要用创建时显示的 `房间 ID` + `客户端 ID` 点击“重连房间”进入。

### 忘记客户端 ID

当前 UI 多人面板会显示当前客户端 ID。联调时请在创建/加入后立即记录。后续可以继续优化为更醒目的复制/展示区域。

### 房主退出后不能重连

这是预期行为。当前策略是房主退出即关闭房间；普通玩家退出才保留重连。
