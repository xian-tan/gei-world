# 多人联机与双回合模式规划

## 目标

在不破坏当前单机严格轮流回合玩法的前提下，逐步引入多人联机所需的“同时回合制”能力。

核心原则：**一套游戏规则，两套回合调度模式**。

- 共同规则继续由 `GameEngine`、单位/城市/战斗/视野等系统负责。
- 回合调度从固定顺序玩家指针抽象为可切换模式。
- UI、AI、未来网络层都通过统一行动接口提交 `GameAction`。

## 两套玩法

### 严格轮流回合 `sequential`

当前默认玩法：

1. 当前玩家行动。
2. 当前玩家结束回合。
3. 切换到下一位玩家。
4. 所有玩家轮完后进入下一整轮，并结算收入、恢复移动力、刷新视野。

适合：当前单机、教程、新手模式。

### 同时回合制 `simultaneous`

多人联机目标玩法：

1. 每一整轮开始时，所有存活玩家都可以行动。
2. 玩家可实时提交移动、建城、生产等行动，服务端即时权威结算并广播事件。
3. 玩家点击结束回合后，本轮锁定，不再允许继续行动。
4. 所有存活玩家都结束后，推进到下一整轮，并统一结算收入、恢复移动力、刷新视野。

适合：多人联机、更快节奏、未来实时事件推送。

## 架构路线

### 阶段 1：抽象回合模式，保持当前行为不变（已完成第一轮）

目标：将当前 `TurnSystem` 的顺序回合逻辑封装成可扩展接口。

主要改动：

- 新增 `TurnMode` 枚举或字符串模式。
- `TurnSystem` 增加：
  - `mode`
  - `can_player_act(player_id)`
  - `end_turn(player_id, ...)`
  - `get_turn_status()`
- `GameEngine` 不再直接判断 `current_player.id == action.player_id`，改为调用 `turn_system.can_player_act()`。
- 当前默认仍为 `sequential`。
- 保持旧 UI 和测试行为不变。

验收：

- 现有测试全部通过。
- 非当前玩家在 `sequential` 模式下仍不能行动。
- 存档加载保持兼容。

### 阶段 2：加入同时回合制核心逻辑（已完成第一轮）

目标：在引擎层支持 `simultaneous`，先不接 UI。

主要改动：

- `TurnSystem` 支持 `ended_player_ids`。
- `simultaneous` 下所有未结束玩家可行动。
- 已结束玩家不能继续行动。
- 所有存活玩家结束后推进整轮。
- 新增 `turn_advanced` / `player_turn_ended` 等事件信息。

验收：

- 同一回合内多个玩家都能行动。
- 任一玩家结束后被锁定。
- 所有玩家结束后进入下一整轮。
- 收入、移动力、视野刷新只在整轮推进时发生。

### 阶段 3：UI 支持本地玩家与回合模式状态（已完成第一轮）

目标：让 UI 不再强依赖“当前玩家就是可操作玩家”。

主要改动：

- `UIClient` 增加 `local_player_id`。
- 选择、建城、生产、移动基于 `local_player_id`。
- UI 展示当前回合模式、已结束玩家、是否可操作。
- 单机默认继续使用 `sequential`。

验收：

- 当前单机体验不退化。
- `simultaneous` 可在测试或调试入口中运行。

### 阶段 4：联机 Session 抽象（已完成第一轮）

目标：为网络层做准备，不直接让 UI 操作真实引擎对象。

主要改动：

- 抽象 `GameSessionClient`：
  - `start_game()`
  - `submit_action()`
  - `get_view_state()`
  - `get_turn_status()`
- 实现 `LocalSessionClient` 包装当前 `GameEngine`。
- 后续 `NetworkSessionClient` 使用同一接口。

验收：

- UI 可通过本地 session 跑通现有单机流程。
- 引擎层测试不依赖 pygame。

### 阶段 5：网络 DTO 与服务端权威原型（已完成第一轮）

目标：实现最小多人联机骨架。

主要改动：

- 定义纯 JSON DTO：行动请求、行动响应、玩家视图、房间状态。
- 服务端维护唯一 `GameEngine`。
- 客户端只提交行动，不直接修改状态。
- 服务端广播 `ActionEvent` 或状态快照。

验收：

- 本机双客户端可加入同一房间。
- `simultaneous` 下双方可同回合行动并结束。
- 服务端拒绝非法行动。

## 距离“可玩的单人/多人 + 轮流/同时”目标评估

当前已经具备**核心引擎基础**，但距离“玩家可在 UI 中自由选择单人/多人、轮流/同时，并完成一局可玩对局”还差一个中等规模的产品化收口阶段。

### 已具备

- 单人默认玩法已可玩：`sequential` + 本地 AI。
- 引擎支持两套回合模式：`sequential` / `simultaneous`。
- UI 已有本地玩家视角基础，可在测试中驱动 `simultaneous`。
- 已抽象 `GameSessionClient`，UI 行动提交开始走 session 接口。
- 已有 `LocalGameSession` 与进程内 `NetworkGameSession` 骨架。
- 已有 `MultiplayerServer` 进程内权威原型，可维护房间、席位、唯一 `GameEngine`、行动鉴权和安全视图。
- 已有纯 JSON DTO：行动请求、行动结果、玩家安全视图、房间状态。

### 还缺的关键闭环

| 能力 | 当前状态 | 距离可玩还差 |
| --- | --- | --- |
| 单人 + 轮流 | 已可玩，默认路径 | 只需保留稳定性回归 |
| 单人 + 同时 | 引擎可跑，UI 有本地玩家视角 | 需要“模式选择入口”和 AI 在同时回合下按本轮提交行动/结束 |
| 多人 + 轮流 | 服务端可维护房间，回合模式可配置 | 需要真实传输层、房间 UI、客户端视图刷新 |
| 多人 + 同时 | 服务端原型最接近目标 | 需要真实传输层、双客户端 UI 接入、事件/状态同步、结束等待提示 |

整体判断：

- **单机可选轮流/同时**：约 2~4 个小阶段。
- **本机双客户端可玩多人原型**：约 4~7 个小阶段。
- **局域网/远程可玩多人原型**：约 6~10 个小阶段，取决于传输层和房间 UI 深度。

## 后续开发项

### 阶段 6：本地双客户端调试入口（已完成第一轮）

目标：不用真实网络，先用两个 `NetworkGameSession` 驱动同一个 `MultiplayerServer`，验证“多人对局流程”完整。

主要改动：

- 新增脚本，例如 `scripts/local_multiplayer_demo.py`。
- 流程：创建房间 -> 加入房间 -> 开始游戏 -> 双方提交行动 -> 双方结束回合 -> 打印双方安全视图。
- 覆盖 `sequential` 和 `simultaneous` 两种模式。

验收：

- 命令行可跑通双玩家房间。
- 两个客户端拿到不同 `player_id` 和各自安全视图。
- 伪造对方行动被拒绝。
- `simultaneous` 下双方结束后推进整轮。

### 阶段 7：单机模式选择 UI（已完成第一轮）

目标：让玩家在开始游戏前选择“单人/本地模式 + 轮流/同时”。

主要改动：

- 开始界面增加模式选择弹窗或快捷入口。
- 单人 `sequential`：保持现有体验。
- 单人 `simultaneous`：本地玩家和 AI 同一整轮内行动，AI 在服务端/session 层自动提交行动并结束。
- UI 显示当前模式、玩家是否已结束、本轮等待状态。

验收：

- UI 可选择 `sequential` 或 `simultaneous` 开局。
- `sequential` 老流程不退化。
- `simultaneous` 中本地玩家结束后不能继续操作，AI 可完成本轮并推进下一回合。

### 阶段 8：多人房间 UI 原型（进程内，已完成第一轮）

目标：先不接真实网络，在 UI 中走 `MultiplayerServer` + `NetworkGameSession`，验证多人产品流程。

主要改动：

- 新增“多人游戏”入口。
- 支持创建房间、加入本机房间、选择轮流/同时、开始游戏。
- 支持本机两个 UI 客户端或一个调试 UI 切换两个客户端视角。
- UI 读取 `serialize_player_view()` 的安全视图，而不是直接信任完整引擎对象。

验收：

- 可在本机模拟两个玩家完成至少一轮。
- UI 能显示房间席位、玩家名、回合模式、结束状态。
- 双方行动都通过服务端权威校验。

### 阶段 9：真实传输层（HTTP + 轮询已完成第一轮）

目标：把进程内 `MultiplayerServer` 暴露为可连接服务。

建议优先方案：

- 第一版用 HTTP + 轮询，降低依赖和调试成本。
- 后续再升级 WebSocket，实现事件实时推送。

主要改动：

- 服务进程：创建房间、加入房间、开始游戏、提交行动、获取视图。
- `NetworkSessionClient` 从进程内调用切换为 HTTP 调用。
- 增加连接错误、重试、房间不存在、玩家断线提示。

验收：

- 两个独立进程可加入同一房间。
- 行动只在服务端执行。
- 客户端周期刷新安全视图。

### 阶段 10：可玩性收口

目标：从“技术可跑”收口到“可玩”。

主要改动：

- 房间等待、开始失败、对手未结束、断线/退出提示。
- 同时回合下的事件消息队列，避免只看到最终状态。
- 当前玩家/本地玩家/对手状态显示更清晰。
- 简单超时或房主强制推进策略。
- 存档策略：单机保留本地存档，多人先不承诺持久化，后续再做房间快照保存。

验收：

- 玩家不看控制台也能完成一局多人原型。
- 至少支持：单人轮流、单人同时、本机多人轮流、本机多人同时。
- 测试覆盖关键流程，`./.conda/bin/python -m pytest` 全部通过。
